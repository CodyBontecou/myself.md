Agents are an application interface. Anything a user can accomplish in the mobile app or dashboard must also be available as a semantic MCP workflow, with the same application rules and observable result. This is the target architecture; the inventory below records current gaps.

## What counts as parity

An agent can discover the capability, inspect the relevant state, supply validated inputs, invoke it under the user's authorization, and verify the result. Expose operations such as updating a profile or exporting its data rather than reproducing taps, modals, or component state. View sorting, filters, and charts map to equivalent data queries and structured results; presentation-only details do not need remote button controls.

UI and MCP adapters call the same application services. Keep environment-free validation and transitions in `core/`, phone I/O in `client/`, and server I/O in `server/`. Share existing services rather than implementing a second set of business rules in MCP handlers. UI state must refresh when an agent changes application state.

Equivalent behavior includes identity, profile limits, native source restrictions, destination validation, schedule opt-in, credential binding, quota accounting, cloud sharing revocation, cancellation, and activity history. For example, deleting a profile must reconcile its scheduled work and cloud permissions through the same path as a UI deletion. Disconnecting on the server must not be described as stopping local recording unless the phone has confirmed that effect.

## Authorization and platform handoffs

Pairing identifies the account and phone. It does not authorize an agent to expand its own data grants, stored-data sharing, or control permissions. Both interfaces enforce the applicable grants and agent-blocking rules. New access requires the user's approval through a trusted owner/device interface. An agent may prepare and initiate that workflow, then observe its outcome.

Ordinary application reads and mutations need real MCP operations. A link to an editor is useful recovery assistance, but it does not implement updating an existing profile. Preserve the authorization and destructive-action confirmations required by the UI; avoid adding blanket confirmation to every agent action when existing authorization already covers it.

OS permissions, OAuth sign-in, payment and restore flows, secure credential entry, and system share sheets can require a person on the phone or in the browser. MCP should return a precise handoff with a supported destination, the required step, and a way to inspect the resulting state. Distinguish opening a screen from obtaining a permission, storing a credential, verifying a purchase, or delivering a file. Keep secrets in the native vault or appropriate server secret store; diagnostics and links expose only safe metadata such as whether a credential is configured.

## Operation contract

- Discovery identifies supported operations, platform limits, required grants, foreground requirements, and unavailable capabilities. Read state includes freshness and device/profile identifiers; absent state is distinct from a disabled setting.
- Validate bounded inputs and return structured outputs. Paginate large reads and preserve source warnings, partial outcomes, and provenance. Data analysis obeys the same data grants as MCP reads, including when the dashboard owner has wider access.
- Server-owned effects can execute on the server. Phone-owned effects use authenticated device dispatch and call existing client services. Define behavior for offline phones, backgrounding, disconnection, blocked agents, and changed permissions before accepting work.
- Queued effects return an operation ID with status and expiry. Expose accepted/queued, awaiting-user, running, completed, failed, cancelled, and expired states where applicable. Link delivery or screen opening is an intermediate result. Success includes the affected identity and resulting state or artifact metadata.
- Mutations support safe retries using an operation/idempotency key. Recheck authorization before execution and reject stale targets or conflicting changes. Expired or revoked operations cannot execute later. Avoid repeating exports, purchases, uploads, or deletion after uncertain delivery.
- Record the initiating agent and outcome in appropriate activity history. Return safe, actionable failures, suggested recovery operations or links, and verification steps. Credentials, private destination URL components, and inaccessible records remain outside responses.

## Implementation order

1. Add capability discovery and safe phone state, then a reusable authenticated phone operation lifecycle with result polling. Verify retries, expiry, revocation, and foreground/offline behavior before relying on it for mutations.
2. Move existing profile mutations behind shared services and expose create/update/duplicate/delete operations. Include stable IDs, stale-change handling, and saved-state verification.
3. Dispatch exports and schedule operations through existing client services. Reuse billing, cancellation, checkpointing, and history; expose complete and partial artifacts.
4. Add permission, recording, credential, cloud authorization, and system-sharing handoffs with observable outcomes. Reuse established native adapters.
5. Expose server analysis and management operations through shared services with agent-specific grants. Complete activity, entitlement and account handoffs.

Completion requires runtime evidence for authorization, side effects and terminal results in addition to the repository's aggregate static check. Device-specific handoffs need device verification; document any unverified platform behavior explicitly.

## Login inactivity and upload diagnostics

Foreground app use renews a local 30-day inactivity window, while background work does not. Expired local sessions are cleared on load/resume. The dashboard continues its existing in-memory session behavior, and MCP clients manage their own refresh tokens under the same provider policy. ## Account deletion

Mobile Settings → Account → Delete account, the dashboard account menu and the public `/delete-account` page share the authenticated owner API (`GET /api/account`, `DELETE /api/account`). `get_account_deletion` exposes the account subject, effects/retention disclosure, state, safe errors and receipt URL. `request_account_deletion` initiates an account-bound browser handoff; the owner signs in and confirms permanent deletion. The semantic `delete_account` MCP tool accepts the same exact subject and `DELETE` confirmation after the user explicitly authorizes deletion, and calls the same account service. Agent OAuth clients cannot invoke the first-party HTTP DELETE endpoint. Account matching protects against confirming a different account after sign-in. Both owner surfaces disclose the same effects and retained purchase identifiers. The optional handoff is for users who prefer to confirm in the browser. Existing agent-blocking rules apply; deletion never expands a data grant.

States are `active`, `running`, `failed`, `completed` and `unavailable`. Phone/upload/request access is revoked at acceptance; completion requires identity removal and physical object cleanup. Idempotent retries and Durable Object alarms resume interrupted cleanup. MCP can inspect status while its original JWT remains valid; the seven-day opaque receipt exposes only state and a safe error after sessions/refresh tokens are deleted. Completed/deleting accounts expose only deletion MCP operations and reject every other account request, including old upload tokens. Hosted identity must be enabled; legacy standalone Keycloak deployments report unavailable.

The initiating mobile UI additionally cancels exports, stops tracking and clears local app data, files, destination credentials, purchase proof and session. Browser/agent handoffs cannot erase copies on another phone or user-owned external storage; the disclosure states that boundary. Native cleanup runs through the same local helper and is covered by SQLite/file/credential fixtures; physical-device behavior and production Apple revocation remain release checks. `npm run verify:account-deletion` verifies real HTTP/MCP ownership and confirmation denials, cloud cleanup, stale-token and upload-grant denial, identity/session/refresh removal, receipt isolation, safe retries and local cleanup boundaries.

## Profile choice and approval

Live queries now choose any saved profile with `agentAccess: true`; Active/Make active are removed.
