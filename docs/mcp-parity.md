## Cloud storage subscriptions

Lifetime is required for paid storage. The 1 GB ($1.99/month, $19.99/year US) and 10 GB ($4.99/month, $49.99/year US) tiers replace, rather than add to, the included 100 MB. Checkout uses store-localized prices. A paid downgrade blocks new bytes above the smaller limit but preserves download/delete and never starts destructive retention while a paid plan remains active.

HTTP, dashboard and MCP lists expose every completed export, including after a downgrade. Upload admission shares a staged/stored count cap of `max(128, ceil(limitBytes / 1_000_000_000) * 128)` (128 included/1 GB; 1,280 at 10 GB), with only the completed daily replacement discounted, bounding temporary overlap to one extra row. The 16 MiB file limit and account byte limit still apply.

Phone-owner `GET /api/cloud/status`, dashboard `workspace.cloudStorage` and MCP `get_cloud_storage` expose the same plan, subscription/store state, byte usage, lapse deadline/bytes at risk, available plans, safe notice-delivery diagnostics and owner handoff. `GET /api/cloud/purchase-account` provides the account-bound UUID; `POST /api/cloud/subscription` verifies purchase/restore and returns that status (402 without verified Lifetime). Only the phone OAuth client may initiate these operations. One subscription chain, including every verifiable Google linked token, belongs to one account; deletion retains ownership tombstones.

Apple active/Billing Grace Period and Google active/grace states preserve capacity only until the provider's recorded expiry; billing retry/account hold/paused/expired/revoked states do not. Hourly reads and Account alarms refresh store truth; verification outages do not invent grace or extend expiry. When paid capacity ends with Lifetime still held and usage above 100 MB, a 30-day lapse starts. Push and email reminders are due on days 0, 23 and 29; successful channels are not repeated during retry, failed deliveries remain recorded and retryable, and the reminder is marked sent only after delivery completes. At day 30 the executor deletes oldest whole exports through the normal physical-object deletion path until usage fits 100 MB and records activity. Renewal or usage falling within 100 MB cancels the lapse. A Lifetime-only legacy overage is not a subscription lapse.

A verified store Lifetime refund/revocation removes all cloud exports immediately, without a 30-day delay, unless another Lifetime purchase or complimentary grant still supplies access. Durable deletion intent survives R2 failures/restarts. The push/email notice explains deletion and tells the owner to cancel any remaining store subscription themselves. Signed Apple Notifications V2 and authenticated Google Pub/Sub callbacks re-read the store, resolve persistent ownership and use the same lifecycle; callbacks cannot grant foreign accounts access or resurrect a revoked chain through replay.

Subscribing/upgrading/restoring requires the owner in `myselfmd://cloud-storage`; managing/canceling requires the App Store or Google Play subscription-settings handoff returned by `get_cloud_storage`. Agents may inspect the current result and direct the owner to these handoffs, but cannot pay, accept terms or cancel on their behalf. Terms: <https://myself.md/terms>; privacy: <https://myself.md/privacy>.

Both runtimes use shared verification and retention services. Workers use per-account alarms, global Purchase ownership objects, identity email and Cloudflare `EMAIL` (sender `support@myself.md`); self-hosted Node polls due account work every minute, retains local SQLite ownership and reuses registered Expo tokens. Node has no Cloudflare email binding: missing delivery is exposed and remains pending, not claimed as sent; a self-hosted transport must be supplied to the shared service for email delivery. `CLOUD_ACCOUNT_EMAILS` may map subjects to addresses for an injected Node transport. Store credentials remain server-only. Google push requires `GOOGLE_PUBSUB_PUSH_SERVICE_ACCOUNT`, with exact audience `${PUBLIC_URL}/api/store/google/notifications`. Existing Apple/Google verification credentials and `IAP_SANDBOX` select the store environment.

Regression assertions are authored in existing `verify-cloud-allowance`, `verify-billing`, `verify-cloud-http`, `verify-worker` and `verify-identity` scripts for these semantics, including signed OIDC refund/physical R2 deletion, transient-provider preservation, staged count caps, complete lists and account-deletion ownership tombstones. They use synthetic accounts, injected store verification/notification delivery and local runtime fixtures, not live purchases. This server recovery did not run checks, deploy a Worker, publish an app or submit App Review; aggregate verification belongs to the integrating parent.

## What counts as parity

An agent can discover the capability, inspect the relevant state, supply validated inputs, invoke it under the user's authorization, and verify the result. Expose operations such as updating a profile or exporting its data rather than reproducing taps, modals, or component state. View sorting, filters, and charts map to equivalent data queries and structured results; presentation-only details do not need remote button controls.

UI and MCP adapters call the same application services. Keep environment-free validation and transitions in `core/`, phone I/O in `client/`, and server I/O in `server/`. Share existing services rather than implementing a second set of business rules in MCP handlers. UI state must refresh when an agent changes application state.

Equivalent behavior includes identity, profile limits, native source restrictions, destination validation, schedule opt-in, credential binding, quota accounting, cloud sharing revocation, cancellation, and activity history. For example, deleting a profile must reconcile its scheduled work and cloud permissions through the same path as a UI deletion. Disconnecting on the server must not be described as stopping local recording unless the phone has confirmed that effect.

## Authorization and platform handoffs

Pairing identifies the account and phone. It does not authorize an agent to expand its own data grants, stored-data sharing, or control permissions. Both interfaces enforce the applicable grants and agent-blocking rules. New access requires the user's approval through a trusted owner/device interface. An agent may prepare and initiate that workflow, then observe its outcome.

Ordinary application reads and mutations need real MCP operations. A link to an editor is useful recovery assistance, but it does not implement updating an existing profile. Preserve the authorization and destructive-action confirmations required by the UI; avoid adding blanket confirmation to every agent action when existing authorization already covers it.

OS permissions, OAuth sign-in, payment and restore flows, secure credential entry, and system share sheets can require a person on the phone or in the browser. MCP should return a precise handoff with a supported destination, the required step, and a way to inspect the resulting state. Distinguish opening a screen from obtaining a permission, storing a credential, verifying a purchase, or delivering a file. Keep secrets in the native vault or appropriate server secret store; diagnostics and links expose only safe metadata such as whether a credential is configured.

## Operation contract

- Discovery identifies supported operations, platform limits, required grants, foreground requirements, and unavailable capabilities. Read state includes freshness and device/profile identifiers; absent state is distinct from a disabled setting.
- Validate bounded inputs and return structured outputs. Paginate large reads and preserve source warnings, partial outcomes, and provenance. Data analysis obeys the same data grants as MCP reads, including when the dashboard owner has wider access.
- Server-owned effects can execute on the server. Phone-owned effects use authenticated device dispatch and call existing client services. Define behavior for offline phones, backgrounding, disconnection, blocked agents, and changed permissions before accepting work.
- Queued effects return an operation ID with status and expiry. Expose accepted/queued, awaiting-user, running, completed, failed, cancelled, and expired states where applicable. Link delivery or screen opening is an intermediate result. Success includes the affected identity and resulting state or artifact metadata.
- Mutations support safe retries using an operation/idempotency key. Recheck authorization before execution and reject stale targets or conflicting changes. Expired or revoked operations cannot execute later. Avoid repeating exports, purchases, uploads, or deletion after uncertain delivery.
- Record the initiating agent and outcome in appropriate activity history. Return safe, actionable failures, suggested recovery operations or links, and verification steps. Credentials, private destination URL components, and inaccessible records remain outside responses.
