# UI and MCP parity

Agents are an application interface. Anything a user can accomplish in the mobile app or dashboard must also be available as a semantic MCP workflow, with the same application rules and observable result. This is the target architecture; the inventory below records current gaps.

## What counts as parity

An agent can discover the capability, inspect the relevant state, supply validated inputs, invoke it under the user's authorization, and verify the result. Expose operations such as updating a profile or exporting its data rather than reproducing taps, modals, or component state. View sorting, filters, and charts map to equivalent data queries and structured results; presentation-only details do not need remote button controls.

UI and MCP adapters call the same application services. Keep environment-free validation and transitions in `core/`, phone I/O in `client/`, and server I/O in `server/`. Share existing services rather than implementing a second set of business rules in MCP handlers. UI state must refresh when an agent changes application state.

Equivalent behavior includes identity, profile limits, native source restrictions, destination validation, schedule opt-in, credential binding, quota accounting, cloud sharing revocation, cancellation, and activity history. For example, deleting a profile must reconcile its scheduled work and cloud permissions through the same path as a UI deletion. Disconnecting on the server must not be described as stopping local recording unless the phone has confirmed that effect.

## Authorization and platform handoffs

Pairing identifies the account and phone. It does not authorize an agent to expand its own data grants, stored-data sharing, or control permissions. Both interfaces enforce the applicable grants and agent-blocking rules. New access requires the user's approval through a trusted owner/device interface. An agent may prepare and initiate that workflow, then observe its outcome.

Ordinary application reads and mutations need real MCP operations. A link to an editor is useful recovery assistance, but it does not implement updating an existing profile. Preserve the authorization and destructive-action confirmations required by the UI; avoid adding blanket confirmation to every agent action when existing authorization already covers it.

OS permissions, OAuth sign-in, payment and restore flows, secure credential entry, and system share sheets can require a person on the phone or in the browser. MCP should return a precise handoff with a supported destination, the required step, and a way to inspect the resulting state. Distinguish opening a screen from obtaining a permission, storing a credential, verifying a purchase, or delivering a file. Keep secrets in the native vault or appropriate server secret store; diagnostics and links expose only safe metadata such as whether a credential is configured.

## Operation contract

- Discovery identifies supported operations, platform limits, required grants, foreground requirements, and unavailable capabilities. Read state includes freshness and device/profile identifiers; absent state is distinct from a disabled setting.
- Validate bounded inputs and return structured outputs. Paginate large reads and preserve source warnings, partial outcomes, and provenance. Data analysis obeys the same data grants as MCP reads, including when the dashboard owner has wider access.
- Server-owned effects can execute on the server. Phone-owned effects use authenticated device dispatch and call existing client services. Define behavior for offline phones, backgrounding, disconnection, blocked agents, and changed permissions before accepting work.
- Queued effects return an operation ID with status and expiry. Expose accepted/queued, awaiting-user, running, completed, failed, cancelled, and expired states where applicable. Link delivery or screen opening is an intermediate result. Success includes the affected identity and resulting state or artifact metadata.
- Mutations support safe retries using an operation/idempotency key. Recheck authorization before execution and reject stale targets or conflicting changes. Expired or revoked operations cannot execute later. Avoid repeating exports, purchases, uploads, or deletion after uncertain delivery.
- Record the initiating agent and outcome in appropriate activity history. Return safe, actionable failures, suggested recovery operations or links, and verification steps. Credentials, private destination URL components, and inaccessible records remain outside responses.

## Current coverage inventory

Browser OAuth sign-in is a user handoff through `/login`. The Cloudflare identity provider sends phone and MCP authorizations there with a signed OAuth query; the Apple/GitHub actions continue that same request, retaining the initiating client's registered callback, state, PKCE and consent. A direct dashboard sign-in uses `qr-dashboard` and returns to `/dashboard/callback`. A loopback callback belongs to the initiating agent and requires its local listener; it must not be replaced with a dashboard callback. Completion is verified by the initiating client's token exchange and subsequent authenticated reads, rather than reaching the login page.

Coverage is based on the implemented routes and tools, not on proposed tool names. A dashboard-only HTTP endpoint is a gap until an authenticated agent workflow exists. Generic URI routing also does not supply an action contract or completion status.

## Implementation order

1. Add capability discovery and safe phone state, then a reusable authenticated phone operation lifecycle with result polling. Verify retries, expiry, revocation, and foreground/offline behavior before relying on it for mutations.
2. Move existing profile mutations behind shared services and expose create/update/duplicate/activate/delete operations. Include stable IDs, stale-change handling, and saved-state verification.
3. Dispatch exports and schedule operations through existing client services. Reuse billing, cancellation, checkpointing, and history; expose complete and partial artifacts.
4. Add permission, recording, credential, cloud authorization, and system-sharing handoffs with observable outcomes. Reuse established native adapters.
5. Expose server analysis and management operations through shared services with agent-specific grants. Complete activity, entitlement and account handoffs.

For each affected capability, update this table with the actual operation and remaining limits. Completion requires runtime evidence for authorization, side effects and terminal results in addition to the repository's aggregate static check. Device-specific handoffs need device verification; document any unverified platform behavior explicitly.

## R2 content storage

The R2 migration keeps mobile and dashboard cloud routes plus `list_cloud_exports`, `read_cloud_export`, and `delete_cloud_export` on the same `CloudStore` logic. It introduces no new app action. Permissions, selected types, upload credentials, quota, billing and history remain account-bound in SQLite; only encrypted content moves to private object storage. Owner deletion waits for the provider effect before returning success, and failures remain retryable. MCP reads recheck sharing/type selections and agent blocking after fetching R2 bytes. Infrastructure migration, backup and rollback are operator CLI tasks outside user-facing MCP.

`npm run verify:r2` exercises the actual S3 SDK against a signed-request HTTP fixture, then reruns authenticated mobile/dashboard/MCP integration with that storage backend. It verifies failed uploads preserve the reservation, incomplete files remain invisible, cross-account reads/deletion fail, explicit sharing and revocation still apply, owner reads and exploration preserve records, and failed physical deletion is reported and retryable. The storage regression also covers in-flight token/grant revocation, encrypted verified backfill, concurrent retries, quota, restart, orphan cleanup, retention and rollback. Existing explorer MCP coverage gaps above are unchanged.

## Cloudflare deployment parity

The hosted Worker and Node fallback use the same HTTP authorization, billing, MCP registrations, cloud operations and dashboard services (`server/application.js` and service factories). Account-scoped Durable Objects retain the same subject namespace, device ownership, sharing selections and agent-blocking checks. Purchase objects enforce one-owner claims across accounts; D1 credential routing does not grant access. Existing purchase and OS handoffs remain user-completed.

MCP stays at `/mcp` on myself.md; the Fly transport is retired after identity cutover. Mobile session/upload transport URLs are canonicalized without changing ownership. Persistent encrypted queue metadata preserves queued profile-delivery state and makes interrupted live requests observable, while native responses remain temporary. Worker restarts release unused agent reservations and retain completed uses. The coverage gaps elsewhere in this inventory still apply.

`npm run verify:worker` runs the actual workerd runtime with signed OAuth fixtures and real MCP clients, verifying ownership denials, claim uniqueness, pairing, cloud effects, concurrent shared quotas and restart persistence. The production cutover also authenticated all seven retained encrypted exports through the live R2 binding. Operator import/export/integrity endpoints are disabled in normal operation and cannot be used by MCP to grant access. Deployment and recovery details are in [Cloudflare migration](cloudflare-migration.md).

## Login inactivity and upload diagnostics

Phone OAuth requests `offline_access`; token refresh is shared across concurrent requests using the same refresh token. Foreground app use renews a local 30-day inactivity window, while background work does not. Expired local sessions are cleared on load/resume. Identity-provider refresh tokens use a rolling 30-day lifetime; generated Keycloak realms configure offline idle expiry without a fixed maximum. The dashboard continues its existing in-memory session behavior, and MCP clients manage their own refresh tokens under the same provider policy. OAuth/secure sign-in remains a user handoff; agents cannot extend the phone’s foreground activity or create an upload grant.

Cloud upload-start and commit errors display the server’s failure with its status. Reauthorization guidance applies only to 401 authentication failures; profile validation, billing and quota failures do not imply logout. `diagnose_phone_export` continues to expose recorded export failures using the existing sanitized history path. Profile upload authorization requires initial approval, then renews automatically with the phone login’s foreground inactivity deadline. `/api/cloud/credential/renew` accepts an existing token proof, owned device/profile and bounded deadline only from the authenticated phone client, calls `CloudStore.renewAuthorization`, and refreshes Worker routing. It cannot create approval, rotate a token, change selections or enable MCP sharing. Background delivery uses the saved foreground deadline. Expired login requires the OAuth user handoff; revoked approval requires the initial profile approval again. Dashboard and MCP sharing/reads keep the same independent grants, and agents cannot renew phone credentials or claim foreground activity. The initial authorization/readiness MCP gaps in the inventory remain.

`npm run verify:disconnect` verifies concurrent session-copy rotation, more than 30 days of continued use, exact inactivity expiry, background isolation, upgrade handling, sign-out races and client delivery of an actual cloud validation failure. Native foreground transitions and the original production 400 response remain unverified without the phone/server response body.

The hosted OAuth handoff uses Workers/D1, keeps the existing issuer and provider user IDs, and requires signed state, S256 PKCE and user consent for agent clients. Agents cannot create first-party OAuth clients or bypass consent through registration. The same verified client identity drives first-party purchase/claim authorization and agent observation in both HTTP adapters. `npm run verify:identity` verifies token exchange, refresh isolation, replay denial, consent, actual MCP calls and first-party denials in workerd/D1.

Credential-renewal regressions exercise expired approval recovery, preserved sharing, revoked-token denial, stale deadline handling and cross-account/device/profile/client denial. `npm run verify:disconnect` checks client foreground/delivery renewal and prevents renewal after login inactivity. Cloud HTTP/MCP and Worker integration cover renewed-token uploads and routing through the same application service. Native foreground transitions remain unverified on a physical phone.

## Account deletion

Mobile Settings → Account → Delete account, the dashboard account menu and the public `/delete-account` page share the authenticated owner API (`GET /api/account`, `DELETE /api/account`). `get_account_deletion` exposes the account subject, effects/retention disclosure, state, safe errors and receipt URL. `request_account_deletion` initiates an account-bound browser handoff; the owner signs in and confirms permanent deletion. The semantic `delete_account` MCP tool accepts the same exact subject and `DELETE` confirmation after the user explicitly authorizes deletion, and calls the same account service. Agent OAuth clients cannot invoke the first-party HTTP DELETE endpoint. Account matching protects against confirming a different account after sign-in. Both owner surfaces disclose the same effects and retained purchase identifiers. The optional handoff is for users who prefer to confirm in the browser. Existing agent-blocking rules apply; deletion never expands a data grant.

States are `active`, `running`, `failed`, `completed` and `unavailable`. Phone/upload/request access is revoked at acceptance; completion requires identity removal and physical object cleanup. Idempotent retries and Durable Object alarms resume interrupted cleanup. MCP can inspect status while its original JWT remains valid; the seven-day opaque receipt exposes only state and a safe error after sessions/refresh tokens are deleted. Completed/deleting accounts expose only deletion MCP operations and reject every other account request, including old upload tokens. Hosted identity must be enabled; legacy standalone Keycloak deployments report unavailable.

The initiating mobile UI additionally cancels exports, stops tracking and clears local app data, files, destination credentials, purchase proof and session. Browser/agent handoffs cannot erase copies on another phone or user-owned external storage; the disclosure states that boundary. Native cleanup runs through the same local helper and is covered by SQLite/file/credential fixtures; physical-device behavior and production Apple revocation remain release checks. `npm run verify:account-deletion` verifies real HTTP/MCP ownership and confirmation denials, cloud cleanup, stale-token and upload-grant denial, identity/session/refresh removal, receipt isolation, safe retries and local cleanup boundaries.
