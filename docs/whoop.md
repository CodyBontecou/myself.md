# WHOOP

The phone follows the `../health-md/apps/apple` integration: a stateless OAuth broker holds the provider app secret, account-scoped device-only secure storage holds rotating user tokens, and the phone reads WHOOP’s v2 API directly. The scope set, eight-character OAuth state, `scope=offline` refresh and mandatory refresh-token rotation match Health.md. No provider secret is bundled into JavaScript.

## Enable a deployment

1. Use the dedicated `myself.md` WHOOP registration (client ID `0e5fa2b7-2456-4a83-9288-df11cb9b4321`) with exactly `myselfmd://whoop`. Its contact is `cody@isolated.tech`, privacy policy is `https://myself.md/privacy`, and initial tier is Sandbox (10 members). Health.md keeps its separate registration and only `healthmd://oauth/callback`; do not reuse its credentials. The existing Health.md broker cannot serve this app unchanged.
2. Configure `WHOOP_CLIENT_ID` and `WHOOP_CLIENT_SECRET` on the myself.md server. Local Node reads the normal ignored `.env`; local workerd uses ignored `.dev.vars`. Hosted Workers use secret bindings declared in `wrangler.jsonc`. Never place secrets in `EXPO_PUBLIC_*`, app config or committed files. The shared authenticated `/api/whoop/oauth` route allows only the phone OAuth client, with `no-store` responses, strict inputs, fixed endpoints and a fixed callback. It fails closed with HTTP 503 without both credentials.
3. Deploy the server and deliver the compatible JavaScript update through the existing release workflow. No native dependency or configuration change is required; the existing `myselfmd` scheme handles the callback.
4. Sign in to myself.md, open Settings → WHOOP → Connect WHOOP, and personally complete WHOOP authentication and consent. Cancel leaves the existing connection unchanged. Reconnect is available when access expires or is revoked.
5. In a profile’s Data selection → Health → WHOOP, select explicit types. Only WHOOP selections do not open HealthKit/Health Connect permission prompts. Local/manual/scheduled exports use the existing profile pipeline. Agent reads additionally require that profile’s Health Agent permission; connecting does not enable it.

Required scopes: `offline read:cycles read:recovery read:sleep read:workout read:body_measurement`. Profile identity/name/email is not requested. The broker passes authorization codes and refresh tokens through to WHOOP without persisting them; health records do not pass through it. Sign-out stops reads but retains account-scoped credentials for the next sign-in. Account deletion erases local credentials. Disconnect revokes WHOOP access before erasing credentials; a failed revoke retains them for retry. Reconnect can recover invalid credentials. Existing exports are not deleted by disconnecting.

## Data contract

| Profile selection       | WHOOP v2 endpoint        | Returned records                                                  |
| ----------------------- | ------------------------ | ----------------------------------------------------------------- |
| `native:whoop.cycles`   | `/cycle`                 | Physiological cycles and returned strain/heart-rate scores        |
| `native:whoop.recovery` | `/recovery`              | Recovery score, RMSSD, resting heart rate and returned physiology |
| `native:whoop.sleep`    | `/activity/sleep`        | Sleep/nap records with exact provider stage durations and scores  |
| `native:whoop.workouts` | `/activity/workout`      | v2 workout IDs, sport names and returned scores                   |
| `native:whoop.body`     | `/user/measurement/body` | Current body profile, explicitly marked as a snapshot             |

The existing `myself.md.export.v1` envelope carries `domain: health`, the namespaced type, `source: whoop`, and the original provider object in `native`. This app exports native records rather than Health.md’s normalized `healthmd.provider.whoop_daily` summary. It preserves unscored/pending states and missing values without calculating scores or inventing zeroes. Millisecond durations and `hrv_rmssd_milli` remain unchanged; they never replace HealthKit SDNN or OS metrics. No OS/provider event deduplication occurs.

Cycles, sleep and workouts use provider `start`/`end` for envelope timestamps. In-progress cycle ends remain null. Recovery has no independent measurement timestamp, so its envelope timestamps are null; retain `cycle_id` and `sleep_id` for joining. WHOOP applies interval filtering. Body measurements have no historical measurement time: the envelope/fetched_at mark capture time, with `capture_kind: current_profile_snapshot`, even for a historical-day export. Warnings explain both cases.

Collections page at up to 25 records using `nextToken`; the app binds the returned cursor to the original query and rejects a repeated immediate cursor. Native advertised responses are limited to 1 MiB and decoded text to 262,144 characters. Native fetch can buffer before the decoded-size check; this is not a streaming transport guarantee. Oversize, authorization and rate-limit failures fail the selected source, allowing the existing partial-export pipeline to report it. Fetches time out and never follow redirects. Refresh is serialized per account and persisted before reuse; concurrent reads share rotation. Reads recheck the signed-in account and saved connection after I/O. Secure-storage failures become structured unavailable status and do not block unrelated OS catalogs/exports.

## Agent and dashboard coverage

`get_phone_data_catalog` includes connection/scopes and selectable WHOOP keys. `query_phone_data` and `get_phone_request` use the same phone adapter, selected types, billing/history and Health Agent permission checks as other Health reads. Query `source` remains the existing phone adapter value `native`; returned record `source` identifies WHOOP. Stored files retain the existing confirmed selection/grant filtering. The owner dashboard can select the synced WHOOP keys and view records through the existing profile/cloud surfaces; authentication remains a phone/browser handoff. The public dataset catalog and shared privacy disclosure describe WHOOP.

`manage_phone_whoop` requests connect/reconnect or disconnect with an owned device ID, operation and caller-chosen request UUID. Reuse the same tuple for retries/status/cancellation. It prompts the owner on the phone and calls the same connect/disconnect functions as Settings. Requests distinguish accepted, awaiting_user, running, completed, failed, cancelled and expired; expire after five minutes; cannot be agent-cancelled after starting; and persist encrypted metadata in hosted account storage. Phone receipts acknowledge effects without repeating them after a lost response. Service restart during running yields failed/uncertain instead of repeating an OAuth or revocation effect. Check the phone before creating another request. A blocked agent or disconnected phone cannot continue pending work. The restricted ChatGPT read-only surface excludes connection mutations but includes permitted WHOOP catalog/record reads.

## All Time provider request candidate — 22 October 2026

The physical-phone baseline produced 1,275 daily files before intentional cancellation; 13 were partial because WHOOP returned rate-limit errors. This is an incomplete baseline, not a completed-export speedup. Four daily WHOOP collection reads across 3,003 days also exceed the provider's [default 10,000/day quota](https://developer.whoop.com/docs/developing/rate-limiting/). Private history and file audits are under `.local/all-time-export-performance/`.

The local candidate uses an operation-scoped WHOOP reader shared by All Time discovery and every daily/history batch. It gates every HTTP attempt, including a 401 refreshed-token retry, at at most 90 in a rolling minute and retries a quota response once after a cancellable minute backoff. For daily reads it probes a containing window of at most 30 days with `limit: 1`. Only a successful, complete, terminal zero-record response proves emptiness; contained daily intervals may reuse that proof for at most 60 seconds. Positive windows retain the actual daily provider queries, payload order and cursors. This relies on monotone interval containment in the documented provider filters and needs real-phone comparison. It does not infer recovery membership from `created_at`, read an unselected related sleep source, or bucket interval-spanning records locally.

Proofs retain no records and stay only in the running operation. Current account, WHOOP connection/token/scope identity, profile validity and existing MCP checks remain gates. Token rotation or connection changes invalidate proofs. A proof is a short bounded snapshot, not a fresh provider authorization request for each skipped day; its covered range, probe start time and maximum age are explicit in file warnings. Delayed dispatch and consumption recheck both MCP approval and current local account/WHOOP connection/scope. Approval-service failures abort as failed exports with their original error; local cancellation remains distinct. A cancelled connection exchange cannot restore credentials. Cancellation and every terminal export outcome prevent delayed dispatch. A token rotation during a probe discards its proof and falls back to a fresh daily query under current consent. Bounded and scheduled exports retain their existing provider transport. Isolated runtime cases pass for proof expiry, concurrent reuse, nonempty/continued/partial/error probes, exact cursor forwarding, scope/connection loss, cancellation and pacing. Physical All Time speed, completeness and memory verification remain pending; no beta release is claimed.
