## Agent workflow

1. Call `list_cloud_exports`, follow all metadata pages, and choose files with `agentPermissions.time` from one phone and profile. If there are several plausible profiles, let the user choose. Do not select a file by an invented identifier. Export `day` describes the export artifact, not necessarily all dates inside it; upload-day filters alone can omit relevant appended or historical records.
2. Resolve an explicit local `weekStart` and IANA `timezone`. The review covers seven completed local days beginning on that date; comparison uses the preceding seven local days. Calendar boundaries honor DST. Current/future unfinished weeks and skipped calendar dates are rejected.
3. Call `review_weekly_screen_time` with one to 32 unique selected `exportIds`. Include both weeks; duplicate snapshots are supported. The service reads only currently permitted screen-time records, following bounded record cursors. A review stops with an error above 200 pages rather than returning a truncated total. Each successful page consumes the existing raw-cloud-read allowance and records access history; a later error does not refund previously successful pages. Narrow the file selection deliberately before retrying.
4. Read the structured `series`, `counts`, `exports` and `warnings`. The card presents this same result. Keep sources, types, granularities and native device names separate; the selector changes presentation without another data read. No cross-series total is provided.
5. Summarize observed usage and top apps. Report gaps, exclusions and partial files. Ask which app or habit the user wants to change and suggest a small experiment; a conversation suggestion does not create a reminder or change phone settings.

Example tool arguments (IDs must come from discovery):

```json
{
  "exportIds": ["<shared export UUID>"],
  "weekStart": "2026-10-08",
  "timezone": "America/Puerto_Rico"
}
```

## Interactive drilldowns

Select either week's daily usage cell to see that day's leading apps. Select a weekly or daily app to see its fourteen daily observations; select a date there to return to that day's app breakdown. Back controls return to the originating day or weekly view. Source switching resets the detail view. Keyboard users can activate the same buttons, with focus moved to the detail heading.

The MCP result exposes the same information in each series' `dayBreakdowns` and `appDrilldowns`. Each day lists up to ten apps and `otherDurationMs`; app trends cover the union of the weekly and daily top tens, at most 150 apps per series. An absent app observation is null, never assumed zero. These are aggregated observed durations, not exact session timelines or causal explanations. All original exclusions and source separation apply before aggregation. Detail selection uses only the result already returned, with no extra reads, charges, persistence or grants. Previously shared results remain subject to the host's retention controls. Earlier card results without detail fields remain viewable.

## Interpretation

Only `time` records of type `application`, `applications`, `websites` or `sessions` with valid timestamps, a usable app identifier/name and finite nonnegative `native.durationMs` no larger than their interval are counted. Unsupported or malformed records are reported as invalid. Native fields are never guessed from elapsed interval length.

Exact repeated observations are counted once across selected files. Conflicting overlapping observations for the same app/source/type/granularity/native device are excluded in full; the service does not arbitrarily pick one snapshot. Records that span local midnight are excluded rather than proportionally dividing an aggregate. Platform limitations can therefore produce gaps, especially daily Android buckets whose boundaries differ from the chosen timezone.

Missing days have `durationMs: null`. Week-over-week change is withheld unless both periods contain observations on all seven days, there are no invalid/cross-midnight/conflicting records affecting comparison, and every selected export is nonpartial. Even then the result is a change in **observed app usage**, not proof of complete collection, unique screen-on time or causation. Concurrent app usage and multi-device account aggregates can overlap. Fictional fixtures are explicitly labeled. Export IDs, artifact dates and upload timestamps are returned as provenance; raw health/location records and destinations are not included.

Ownership and source selection checks run before reads. Permissions are checked around asynchronous storage access; grants and file identity must remain unchanged throughout a review. Revocation fails the review without returning a partial result. Copies previously sent to ChatGPT remain subject to its retention controls.
