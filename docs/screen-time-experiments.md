# Personal screen-time experiments

Choose an app in the weekly review, open its daily trend and set a daily cap in minutes, a local start date and an optional action to try. The card defaults to tomorrow in the review timezone. The experiment lasts seven local days, starts after the completed baseline ends and is saved to the account across chats. It does not create a reminder, change phone limits, start capture or grant data access. Already-started periods are explicitly labeled retrospective.

## Tools and application logic

Both full MCP and the restricted ChatGPT connection expose:

- `save_screen_time_experiment`: a user-chosen app, exact review series, daily cap (0–1440 whole minutes), start date, optional plan (300 characters), completed baseline start, explicit IANA timezone and discovered baseline export IDs. Supply a new UUID `requestId` for a new goal; reuse identical arguments for safe retries. A completed retry returns the existing goal without another baseline read. Concurrent first attempts can still consume normal page reads. A reused ID with different arguments fails.
- `list_screen_time_experiments`: saved settings, baseline observations, start/end/review dates, current phase and latest evaluation, subject to current grants. The account limit is 100 retained experiments, including cancellations. List/cancel do not read exports or consume the record-read allowance.
- `review_screen_time_experiment`: after `reviewAfter`, select discovered shared export IDs from the saved phone/profile. The same bounded, authorized, billed and audited read path used by weekly reviews reads the experiment period. The result matches the saved source, native type, granularity, native device label and app identifier, and saves the latest evaluation and provenance. A target app is retained even when it falls outside the review's top-ten display.
- `cancel_screen_time_experiment`: stops a saved goal while retaining history. Retries are safe. An owned goal can be cancelled by its discovered ID after sharing is revoked; the response acknowledges only its ID and cancellation, without disclosing saved observations.

The optional card uses these same tools over the standard MCP Apps bridge. New calls advertise `ui://myself-md/weekly-screen-time-review-v2.html` to avoid cached earlier renderers; the original resource URI remains readable for old cards. Saving explicitly describes the additional baseline reads and allowance. Reviewing discovers shared metadata with exact saved phone/profile filters, follows cursors and rejects selections over 32 files rather than silently truncating; a conversational agent can help narrow the files. The UI never filters only by artifact dates. The tools retain the existing 200-page record limit and stop without a partial result after permission/file changes. Successful pages before a later failure still count.

## Outcome interpretation

The goal is a daily cap, not a weekly average. `within_goal` means every one of seven usable observed app days is at or below the cap. `above_goal` means at least one is above it, with seven usable observed days available. Missing app observations remain null even when other apps have records. Missing days, partial files, invalid/cross-midnight records or conflicting overlaps make the result `inconclusive`. Diagnostics explain these blockers, and sharing additional complete exports permits another review. Explicit zero-duration observations remain zero.

The baseline and outcome use the weekly review's exact deduplication and exclusions. Change from baseline is reported only when both measurements are usable; the goal itself can be saved with an incomplete baseline. Even seven observed days do not prove complete collection. Results describe observed usage and cannot establish that an action caused a change. A retrospective goal is useful for exploring the workflow, not evidence of an intervention.

Phases are `upcoming`, `in_progress`, `ready_to_review`, `awaiting_data`, `reviewed` and `cancelled`. Premature review fails before record reads. A goal cancelled during an awaited read cannot acquire a new saved evaluation. Plan text and app labels are data, never instructions, and render as text nodes.

## Storage and authorization

`screen_time_experiments` is an account-scoped SQLite table with an encrypted payload, using the existing cloud AES-GCM codec and distinct subject/experiment associated data. Only the owning account can load or change a goal. Saved observations also require the profile's current Screen time Agent grant and selected native type; revocation hides them without letting an agent self-grant access. Copies previously returned to a host remain subject to that host's retention controls. Cancellation retains history; account deletion removes the table's owned rows. The table participates in account import/export migration. Phone and dashboard UI actions are unchanged.

The pure measurement/evaluation logic lives in `core/screen-time-experiment.js`; storage and semantic operations are in `server/screen-time-experiment-store.js` and `server/screen-time-experiments.js`. `server/screen-time-review.js` provides the shared review loader and returns phone/profile scope for goal creation. The same self-contained renderer handles weekly reviews and experiment results without remote assets or direct network connections.
