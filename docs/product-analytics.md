# Product analytics

The hosted Cloudflare service stores explicit, consented product events in a separate D1 database (`ANALYTICS`). Cloudflare Web Analytics continues to provide independent aggregate website traffic/performance data. This implementation has no third-party analytics SDK or session replay.

## Collection and consent

The iOS/Android welcome screen and Settings → Privacy contain **Share usage analytics**, initially off. Website, documentation, blog, pricing and dashboard pages offer Allow usage analytics / Keep analytics off and a persistent Analytics preferences control. Browser Do Not Track / Global Privacy Control stops delivery. Demo, QA, shared-profile renderers, account-claim/deletion pages, OAuth authorization forms and operator pages are excluded. Dev phone builds require `EXPO_PUBLIC_ANALYTICS_ENABLED=1`; release builds still require user consent. No new native dependency or permission is needed.

Clients queue at most 200 events, send at most 25 in one bounded request, retain stable retry IDs, and discard events older than seven days. Mobile uses existing SQLite-backed storage; browser consent is local-storage scoped, with each tab's outbox/anonymous ID in session storage. Anonymous browser-tab users and app-install users remain separate until sign-in links them. Event timestamps allow up to five minutes of clock skew. Event names, surfaces and optional step categories are allowlisted; unknown properties, free-form text and oversized inputs are rejected. No records, paths, URLs, source selections, profile names, emails, token strings, raw errors or IP addresses are stored in analytics tables. The public endpoint is rate limited using Cloudflare's IP-based limiter without storing the IP in D1.

Account preferences are shared by HTTP and MCP. Explicit local consent carries into an account only when it has no prior choice; a server-side opt-out wins. Account switches and sign-out rotate local identity and drop pending old-account events. Authenticated collection checks the account preference on every send. Revocation erases account-linked and aliased anonymous events, retains a disabled pseudonymous preference, and blocks linked anonymous identifiers for 180 days against delayed replay. Collection writes recheck revocation inside the D1 batch. Account deletion uses the same erasure boundary and remains failed/pending if it cannot complete. Unlinked anonymous records expire within 180 days; disabling a signed-out browser/install stops its future collection but cannot identify copies in other tabs/devices.

## Events and interpretation

- Website: page views, sign-in attempts, actual App Store/Google Play link clicks. Current disabled coming-soon store badges do not count as clicks or installs.
- Phone: foreground opens, onboarding entry/steps/completion, saved profiles, paywall views and manual/scheduled export outcomes. Partial and cancelled exports are separate from success/failure. Export events originate after local history persistence; the completion event follows the exporter outcome. They are client reported, not proof independently verified by the server.
- Dashboard: authenticated sign-in/entry and page views. Operator reporting is excluded from collection.
- Server: newly created identities (creation timestamp verified against identity D1 when a consented user sends activity within 24 hours) and completed phone claims. A claim event is not proof of granted data access or query readiness. Pairing events have a `server` surface because the claim does not establish iOS/Android; they appear in all-surface reports.

`/api/analytics/anonymous` accepts bounded public client events. `/api/analytics/events` accepts authenticated first-party phone/dashboard events and derives the actor from the verified token. Neither accepts client assertions of signup or pairing completion. Public event collection is inherently client-reported and can be fabricated; only server milestones are marked verified. A public event endpoint is not an authenticated business ledger.

## Reports and access

Reports default to **Customer activity**, excluding known internal identities. **Internal and QA** and **All activity** keep those events available for diagnostics without deleting them. The `audience` filter (`customers`, `internal`, `all`) applies to event counts, daily activity, both funnels and retention, after resolving account aliases. Operators (the subject allowlist and linked GitHub owner), the reviewer identity, explicitly configured test accounts and known anonymous test identities are internal. This is an exclusion filter, not proof that every remaining anonymous visitor is a customer. Unidentified historical QA remains unclassified; do not infer identity from country, device or a familiar event pattern.

Private Worker configuration can add comma-separated `ANALYTICS_INTERNAL_SUBJECTS` (exact namespaced account subjects), `ANALYTICS_INTERNAL_ANONYMOUS_IDS` (32-character client IDs) and `ANALYTICS_INTERNAL_KEYS` (64-character stored pseudonyms). The Worker hashes raw identities internally and never returns them in reports. Keep actual owner/test values in private deployment configuration; checked-in defaults are empty. Account exclusions also cover anonymous history linked to those accounts. Existing consent, erasure, retention and report authorization still apply. Exclusions classify stored activity; they do not grant access or change collection consent.

The operator page has **Exclude this browser** / **Include this browser**. It stores only the one-year `myself_internal_traffic=1` exclusion preference, scoped to that browser, including signed-out visits. Product-event delivery stops while excluded, without changing usage consent. A Cloudflare Configuration Rule disables automatic RUM injection for that cookie, `X-Myself-QA: 1`, `HeadlessChrome` and the operator report page. The QA header affects website measurement only; use isolated fixtures or a configured identity for product QA. Keep the existing automatic injection and EU exclusion settings. The local browser action must be repeated in other browsers/private windows; an MCP report provides the setup URL and browser handoff because a remote agent cannot set a different device's cookie. Historical anonymous Cloudflare page views cannot be reliably reclassified; website reports exclude flagged bots and disclose the remaining uncertainty.

Open `/operator/analytics` or the operator-only **Product analytics** dashboard account-menu entry. The page shell contains no private data; every report request requires verified OAuth and operator authorization. It shows an ordered visit → signup → onboarding → first successful export funnel, a separate app-first onboarding → completion → export funnel, independent milestone totals, daily active users, and exact UTC day 1/7/30 retention after the first recorded successful export. Dates are inclusive start/exclusive end, at most 90 days. Surface filters apply to individual events, not acquisition cohorts. Omit the filter for cross-platform journeys.

Funnels require each step in order within the report range. Existing users, app-first acquisition, onboarding before signup, denied analytics consent, browser blocking and unlinked app-store installs can all reduce the combined funnel. Independent counts and the app-first funnel make those gaps visible. Retention uses first successful export in retained history, excludes incomplete UTC days from eligible cohorts, and does not confuse an immature cohort with 0% return. Retained history is 180 days, so this is not an all-time first-export claim. Reports use unsampled SQL aggregates and return no raw actor identifiers.

`ANALYTICS_OPERATORS` is a comma-separated allowlist of exact namespaced account subjects. Alternatively `ANALYTICS_OPERATOR_GITHUB_ID` selects a verified linked GitHub account through identity D1; the checked-in value is the same owner GitHub ID used by the existing support service. Set it empty to use only the subject allowlist. Reviewer accounts are always denied. A user's profile grants never grant analytics report access. Full MCP exposes:

- `get_usage_analytics_preference`: current account's choice.
- `set_usage_analytics_preference`: same validation and erasure as UI. Enabling requires explicit owner consent and `ALLOW_USAGE_ANALYTICS`; an agent must not infer consent from its own interest in reports.
- `get_product_analytics_report`: discovered only for operators; authorization is rechecked for every report. Blocked agents are denied. The restricted ChatGPT resource does not expose these tools.

Local signed-out preferences have no authenticated account to address over MCP; enabling them requires the owner in that browser/app. MCP can manage the shared account preference after authentication. These choices do not grant access to health, usage, location or export data.

For provisioning another environment or releasing a later change:

1. Create `myself-md-analytics` using `npx wrangler d1 create myself-md-analytics`, and record the returned `database_id` on the `ANALYTICS` binding in `wrangler.jsonc` (Wrangler can also provision omitted IDs at deploy).
2. Apply `npx wrangler d1 migrations apply myself-md-analytics --remote`. The migration directory is `worker/analytics-migrations`.
3. Verify the operator mapping and existing `IDENTITY_SECRET`, which HMACs separate account, visitor and event namespaces. Do not rotate it independently without a migration: changing it disconnects preferences, deletion lookup and identity links.
4. Run `npm run worker:types`, `npm run dashboard:build`, `npm run format`, `npm run check`, `npm run verify:analytics`, and `npm run bundle`.
5. Deploy the Worker with its new binding and rate limiter using the normal release process; publish a compatible phone JS update/build from the current local main checkout. The existing daily Worker scheduled handler removes expired analytics events, alias mappings and replay tombstones.

For local development, apply the same migration with `--local`. The Node/self-hosted server returns an explicit hosted-service requirement for analytics routes and does not install a separate analytics backend. The Worker fixture provisions isolated analytics/identity D1 databases, exercises actual HTTP/JWT/MCP authorization, consent, aliasing, deduplication, erasure and mature/immature retention. Browser tests use synthetic OAuth exchange responses but real report authorization and SQL. The shared outbox tests cover opt-in, offline persistence/retry and account switches. Both real mobile JS adapters are executed with synthetic native/network boundaries to verify platform labels, anonymous consent, account linking, server opt-out and account-switch isolation. Native provider authentication, physical-device delivery, store acquisition attribution and production operator sign-in remain separate checks.
