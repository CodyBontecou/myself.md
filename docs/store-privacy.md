# Store privacy reconciliation

19 October 2026. App Store Connect app `6821601165` and Google Play package `com.myself.md` were inspected in the signed-in consoles against current canonical source, the live 18 October privacy policy, TestFlight 17 and Play internal 17. This updates the historical [Play audit](google-open-beta.md); it does not establish store approval or public availability.

## Saved declarations and publication boundary

Apple initially had no data declaration and no policy URL. Both policy links are now saved: `https://myself.md/privacy` and the optional choices link `https://myself.md/privacy#revocation-and-deletion`. All 19 selected categories have completed purpose, identity-linkage and tracking answers. Every category is declared linked to the user and used for App Functionality; User ID, Device ID and Product Interaction additionally declare Analytics. No category is used for tracking, advertising or marketing. Account-linked exports and diagnostics mean that the category cannot be described as entirely anonymous merely because some Expo traffic is unlinked. After the owner explicitly approved the final accuracy, review-guideline and applicable-law attestation, Publish completed. App Store Connect confirms **Published a few seconds ago by Cody Bontecou**, with all 19 categories and both policy links retained. This publishes the privacy responses; it does not submit an iOS app version or establish public App Store availability.

Google's existing 18 collected categories remain selected, non-ephemeral and with the existing collection optionality. Four purpose entries were corrected and saved in Publishing overview:

- User IDs: add Analytics and Fraud prevention, security, and compliance.
- App interactions: add Analytics.
- Device or other IDs: add Analytics and Developer communications.
- Email address: add Developer communications for transactional cloud-storage notices.

Crash logs and Device or other IDs remain required because automatic Expo update/recovery requests have no in-app opt-out. The remaining 16 categories remain optional: account sign-in, purchases, source permissions, exports and diagnostic sharing have separate choices. Optional product analytics does not make automatic Expo identifiers optional. OAuth account creation, TLS transport, account deletion and separate data-deletion links were verified in the saved form. Name, email and photo purposes do not include Analytics: the collector does not store those values.

Google reports an 18 October rejection, **Invalid Privacy policy → Data retention policy not specified**. The saved URL was already `https://myself.md/privacy`. A fresh unauthenticated browser read shows explicit cloud, local, query, analytics and deletion-marker retention, dated 18 October. The saved Play URL now points to `https://myself.md/privacy#cloud-storage-and-retention`, highlighting that section of the same complete policy. Changing the link does not prove that Google has accepted the correction; the rejection stays open pending review. No production policy or backend deployment was needed for this audit.

Publishing overview contains **three** changes: Privacy policy, Data safety, and a pre-existing **Open testing → Track status → Resume track**. Its track action menu exposes View change; Save for later was disabled during quick checks. Automatic approval review initially rejected clicking Submit 3 changes for review because resuming open testing was outside the declaration request. The owner then explicitly approved all three changes, including the open-test resumption. The submission and final Send changes for review confirmation completed; Publishing overview now lists all three under **Changes in review**. Google review acceptance, resolution of the retention-policy finding and actual open-track availability remain unverified. No new binary or additional release change was added by this task.

Google's “No data shared with third parties” remains the existing classification using its service-provider and informed user-initiated-transfer exemptions. It does **not** mean that no recipient receives data. Cloudflare/Expo process infrastructure data; OAuth providers authenticate; users choose remote export destinations and approve profile access for agents/AI providers. The current consent disclosures warn about AI-provider retention and copies already delivered. Transfers outside those exemptions require a new declaration; agents cannot consent for the user. Advertising, data-broker transfers and advertising identifiers are not app capabilities found in this audit.

Camera pairing scans, system credentials/Face ID and native payment entry are not declared as photo, biometric or card uploads merely because the app invokes those system flows. OAuth avatar storage independently justifies Photos. Sensitive Info is included for supported reproductive-health records, not for Face ID. No new data capture or physical-device interaction occurred during this reconciliation.

## Retention and deletion consistency

The live policy discloses exports until deletion/replacement/account deletion, the 30-day paid-storage lapse exception, immediate export deletion on Lifetime refund/revocation, one-hour unfinished uploads, and 90-day activity cleanup on access. Phone files/points do not expire automatically. Live query access expires five minutes from request creation; logical expiry and subsequent memory cleanup are distinct. Analytics events expire within 180 days, retry queues within seven days, and revocation erases linked events. Deletion receipts last seven days plus routing cleanup; pseudonymous credential-rejection, unlinked purchase identifiers and analytics retry guards remain with the stated limits. Account deletion does not cancel store subscriptions or recall external copies. The subsequent [19 October production disposable-account rehearsal](launch-privacy.md#production-disposable-account-deletion--19-october-2026) verified Apple grant invalidation, identity erasure and deletion of seven exact R2 objects. Those runtime results are separate from store publication or Google policy acceptance.

Existing phone/dashboard consent and MCP operations continue to use the same profile grants, analytics preferences, data reads, deletion workflow and shared `get_privacy_policy` disclosure. This task changes store metadata and documentation only; it grants no access, changes no collection default and adds no user-facing action requiring a new MCP operation.
